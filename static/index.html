Database Schema & Multi-Tenant Hierarchy Architecture

Julley Online Collaborative Platform • Data Isolation & OCC Modeling

Multi-Tenant Hierarchy

Organization → Tenants (Branches) → Boards → Columns → Tasks.
Data isolation is enforced at the database level by partitioning business entities with tenant_id foreign keys and indexes. Cross-tenant queries are blocked via authenticated middleware dependencies that verify user memberships.

TABLE organizations
  • id VARCHAR(36) [PK, UUID]
  • name VARCHAR(100)
  • slug VARCHAR(100) [UNIQUE]
  • created_at, updated_at TIMESTAMP
TABLE tenants (Branches)
  • id VARCHAR(36) [PK, UUID]
  • org_id VARCHAR(36) [FK -> organizations.id]
  • name VARCHAR(100)
  • slug VARCHAR(100)
  • location VARCHAR(100)
  • created_at, updated_at TIMESTAMP
TABLE memberships (RBAC)
  • id VARCHAR(36) [PK]
  • user_id VARCHAR(36) [FK -> users.id]
  • org_id VARCHAR(36) [FK -> organizations.id]
  • tenant_id VARCHAR(36) [FK -> tenants.id, NULLABLE]
  • role VARCHAR(30) [org_admin, tenant_admin, member]
TABLE tasks (OCC & Fractional Indexing)
  • id VARCHAR(36) [PK]
  • tenant_id VARCHAR(36) [FK -> tenants.id, INDEX]
  • board_id VARCHAR(36) [FK -> boards.id, INDEX]
  • column_id VARCHAR(36) [FK -> columns.id, INDEX]
  • title VARCHAR(200)
  • order FLOAT [Fractional Index: O(1) DND]
  • version INT [OCC Version for 409 Conflict]
  • assignee_id VARCHAR(36) [FK -> users.id]

Advanced Concurrency & Drag-and-Drop

1. Optimistic Concurrency Control (OCC):

Each task has an atomic version integer. Updates send expected_version. If mismatched, the server rejects with HTTP 409 Conflict and provides the latest snapshot for 3-way resolution.

2. Fractional Indexing (LexoRank):

Reordering computes midpoint (prev + next) / 2.0. Only the moved task row is updated—zero mass table locks or drag-drop reordering conflicts!
